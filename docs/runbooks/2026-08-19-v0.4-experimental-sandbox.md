# DSH Guard v0.4 实验性 Sandbox 运行手册

> 版本：`0.4.0-alpha.2`
> 平台：macOS 26.4.1 实机验证；依赖 deprecated `/usr/bin/sandbox-exec`
> DSH：`0.1.0-rc.7`；Node：`22.22+`

## 这项功能解决什么

默认关闭的 Agent 操作保护只能拦截 DSH 正规工具调用。恶意 Host 插件可以绕过工具层，直接调用 Node `fs`、`net/fetch` 或 `child_process`。`sandbox run` 把整个 DSH Host 放进 macOS 内核 policy：未允许的文件、网络与 executable 会得到 `EPERM`。

这是整进程隔离，不是逐插件隔离。DSH Core、主 Agent、Companion 和所有插件共享允许的 workspace、网络与环境变量，因此主 Agent 的文件、Shell 和网络能力也会被限制。

## 启动前

1. 使用 Node `22.22+` 运行 `dsh-guard`。
2. 若 `dsh` 不在 PATH，设置精确 rc.7 入口：

   ```bash
   export DSH_BIN=/absolute/path/to/@deepseek-ai/dsh/lib/bin.js
   ```

3. 目标 profile 必须已经由 Guard 纳管且当前为 `verified`：

   ```bash
   dsh-guard verify --profile web
   ```

4. 退出正在使用同一 profile 的 DSH GUI。
5. 只把真正需要的项目目录作为 workspace；不要选择 home 或宽泛父目录。

## 先看计划

```bash
dsh-guard sandbox plan \
  --profile web \
  --workspace /absolute/project \
  --network loopback
```

需要机器读取时加 `--json`。human 输出包含 canonical workspace、环境变量名、warning 和 policy hash；JSON 还包含完整 SBPL 与全部计划路径。两者都不包含环境变量值、profile 内容或文件内容。

`plan` 会临时复制 profile 以准确编译 rc.7 可运行的 policy，输出后立即清理副本。每次运行副本路径不同，所以预览和随后 `run` 的 policy hash 不要求相同。

## 启动 DSH

```bash
dsh-guard sandbox run \
  --profile web \
  --workspace /absolute/project \
  --network loopback \
  -- --port 8080
```

`--` 后是原始 DSH app 参数。显式 Host 只能是 loopback：

```bash
dsh-guard sandbox run \
  --profile web \
  --workspace /absolute/project \
  -- --host 127.0.0.1 --port 8080
```

`--host 0.0.0.0`、另一个 `--profile`、未知网络模式、未纳管/漂移 profile 和非 macOS 平台都会在启动前失败；不会回退成普通 DSH。

## 网络模式

| 模式 | loopback bind | loopback outbound | 公网 outbound | 适用场景 |
|---|---:|---:|---:|---|
| `deny` | 允许 | 拒绝 | 拒绝 | 只看 UI、离线检查、`--dump-config` |
| `loopback`（默认） | 允许 | 允许 | 拒绝 | 本机模型或本机代理 |
| `unrestricted` | 允许 | 允许 | 允许 | 明确需要公网 API；不能防止可见数据外传 |

macOS sandbox 不能可靠按 DNS 域名过滤。需要域名 allowlist 时，应把 `loopback` 与进程外代理组合使用。

## 环境变量与凭据

子进程环境从空集合重建。额外变量必须逐个允许：

```bash
dsh-guard sandbox run \
  --profile web \
  --workspace /absolute/project \
  --allow-env OPENAI_API_KEY \
  -- --port 8080
```

credential/token 类名称会显示高风险 warning，因为同进程中的任意插件都能读取它。`NODE_OPTIONS`、`NODE_PATH`、`DYLD_*`、`LD_*`、PATH 与 Guard/DSH 路径变量不能透传。

真实 `~/.dsh/.credentials.yaml` 不会复制或开放。因此依赖该文件的模型调用默认不可用；v0.4 尚无 Secret Broker。

## 一次性 profile

rc.7 启动时会重写 `cordis.yml`，真实 profile 不能直接只读运行。Guard 的实际顺序是：

1. 验证真实 profile；
2. 复制到 `~/.dsh-guard/sandbox-runs/run-*`，不复制 `.credentials.yaml`；
3. 重新计算五个控制文件 fingerprint；
4. 只把副本放进 sandbox；
5. DSH 退出后安全删除副本。

真实 profile 不在 sandbox allow policy 中。Guard state 为维持插件状态、事件和可选 Agent 操作保护仍可读写，所以它不具备对同进程恶意插件的 tamper-proof 保证。

## executable 限制

policy 允许精确 Node binary 和 `process-fork`，但不允许 `/bin/sh`、`/usr/bin/true`、下载后的程序或其他 executable，所以 DSH Bash 工具不可用。再次执行同一个 Node binary 在 SBPL 中无法与首次启动区分，但仍继承完全相同的文件和网络限制。

## 审计

`run` 在 spawn 前向 `~/.dsh-guard/audit.jsonl` 追加：profile、来源 fingerprint、network、workspace digest、允许的环境变量名、plan digest 和 policy hash。它不保存环境值。

```bash
tail -n 1 ~/.dsh-guard/audit.jsonl
```

## 验证实现

纯单元与回归：

```bash
pnpm check
```

真实 macOS 内核边界：

```bash
pnpm test:sandbox
```

成功时必须同时看到：workspace read/write 为 `allowed`，workspace 外读取、其他 executable 和公网为 `EPERM`，loopback outbound 为 `allowed`。

精确 rc.7 与完整生命周期：

```bash
DSH_NODE=/absolute/path/to/node-22.22-or-newer \
DSH_BIN=/absolute/path/to/@deepseek-ai/dsh/lib/bin.js \
pnpm test:e2e
```

E2E 使用临时 DSH_HOME 与 Guard state，完成 scan、approve、双插件 lifecycle、Agent 操作保护默认关闭状态与历史审计可见性、Host API、sandbox plan 和 sandboxed `--dump-config`，最后清理临时目录。显式启用后的工具门禁由独立 ToolRuntime 集成测试覆盖。

## 常见失败

- `profile ... is unknown/drifted`：先用 `verify` 查明原因；不要绕过，必要时先 repair 或重新纳管。
- `Workspace root overlaps ...`：选择更窄的项目目录。真实 DSH_HOME、Guard state、runtime、SSH/GPG/云凭据、Keychain 和 Chrome profile 不能作为 workspace。
- `DSH executable not found`：将 `DSH_BIN` 指向精确 `lib/bin.js`。
- DSH 功能返回 `EPERM`：该功能访问了未允许文件、网络或 executable；收窄理解后显式增加 workspace/网络/环境能力，不要改成 `allow default`。
- 模型凭据不可用：这是默认不复制 `.credentials.yaml` 的预期结果；显式环境变量会对所有插件可见。
- macOS 更新后 policy 无法启动：`sandbox-exec`/SBPL 已 deprecated。停止使用该模式并重新跑 compatibility spike；不要自动降级普通 DSH。
